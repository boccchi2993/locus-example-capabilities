# Capability Authoring

Use this skill when the user asks for a new capability ("make me a capability
that …", "做一个……的能力"). You design the capability, write the project, test
it, and package it into a deterministic `.locus` file the user imports with
one click. The judgment and the rules live here; the machinery lives in this
capability's plugin — `import locus_capability_sdk as sdk` works in any Python
block, and so does the command line `python -m locus_capability_sdk`.

## 1. Judge what to build

Start by asking whether a new capability is needed at all:

- If your existing tools can do the task in this conversation, just do it.
  A capability is for work that will be reused by later tasks, not for one-offs.
- Knowledge or process guidance only (how to structure a report, how to review
  a document) → a **skill** alone.
- A deterministic computation that later tasks will reuse (parse a file format,
  score text, convert units) → a **plugin**: a pure-Python wheel the runtime
  installs offline before tasks run.
- The task needs a third-party Python library (python-docx to write Word
  files, Pillow to process images, …) → still a plugin capability: vendor the
  library's wheel, with its full dependency closure, as wheel plugins (§4).
  When the standard library can do the job simply, prefer the standard
  library — every vendored wheel is weight the user's package carries and
  installs.
- The task needs an external HTTP API → a **skill that uses curl with a
  declared credential**; the user connects their key once and it is injected
  only into approved requests that stay inside the declared target.
- Not supported in this version: MCP servers, and plugin code that opens
  network connections — Python code cannot reach the network at all (§3).

Skills and plugins usually pair up — the plugin computes, the skill teaches
when and how to call it. If a request mentions an API key, that is a credential
declared in capability.json; never hard-code keys in code or text.

## 2. Project layout and rules

A capability project is one directory:

```
<project>/
  locus.json                       # author, title, purpose, changelog (not packaged)
  capability.json                  # the capability descriptor
  skills/<skill-id>/skill.json     # one descriptor per skill
  skills/<skill-id>/SKILL.md       # the skill text (what the model reads)
  plugins/<plugin-id>/plugin.json  # one descriptor per plugin
  plugins/<plugin-id>/artifacts/   # the wheel, written by build_wheel
  src/<python-package>/...         # plugin source (not packaged)
  tests/...                        # optional (not packaged)
```

Where to put the project: `/mnt/workspace/capabilities/<id>/` when
`/mnt/workspace` is mounted, otherwise `/home/locus/capability-projects/<id>/`.
Files outside the declared package (src/, tests/, locus.json, README.md) are
ignored by the packager — they never enter the `.locus` and never cause errors.

Rules the SDK enforces (`sdk.validate` prints one diagnostic per violation):

- **ids** are lowercase letters, digits, dot, dash, underscore (`text-tools`,
  not `Text Tools`); the project directory name is the capability id.
- **versions** have three numeric parts (`1.0.0`). Every repack of changed
  content bumps the patch part first (`1.0.1`, `1.0.2`, …) — the version is in
  the `.locus` filename and in the user's replace prompt, so the same version
  must never mean two different files.
- **capability.json** fields: schemaVersion 1; id, version, displayName,
  description, plugins, skills, mcps. `credentials` only when the task really
  needs an external API. The `plugins` array lists wheel-plugin ids (§4)
  dependencies-first, right beside any own plugin ids.
- **plugin.json**: runtime "python", authority "none", `provides.pythonImports`
  listing the exact importable package names, and exactly one artifact
  `artifacts/<dist>-<version>-py3-none-any.whl`. Wheel plugins (`py-…` ids,
  §4) follow the same shape and are generated by `sdk.plugin_from_wheel` —
  never written or edited by hand.
- **skill.json**: id, version, displayName, description, and `"source":
  "SKILL.md"`.
- **locus.json** (not packaged): author, title, purpose (both go into the
  package manifest), changelog (a list; the first entry notes the date of the
  first version).
- **credentials**: name (`UPPER_SNAKE`), label, description, origin, pathPrefix,
  header (`Authorization`, `X-Api-Key`, or a custom `X-…` name), scheme
  (`Bearer` or omitted). The origin must be an `https://` public DNS host with
  no path. **Never declare a credential for an `http://` address or for a
  private, loopback or local host** (localhost, 127.0.0.1, 10.x, 192.168.x,
  `.local`, `.internal`, …) — the SDK refuses to package it and import refuses
  to install it.
- **curl in skill text**: a credential variable may appear only in a request
  header's value, spelled exactly as declared — `-H "Authorization: Bearer
  $NAME"` with scheme Bearer, or `-H "X-Api-Key: $NAME"` without — and the
  request URL must stay inside the credential's origin + pathPrefix. `$NAME` in
  a URL, body, or any other command is left as literal text and rejected by the
  skill rules. Never write a real key value; the variable is the only accepted
  form.

## 3. Locus environment limits

- One Python program = one separate bash call, wrapped in a quoted heredoc:
  `python <<'PY'` … `PY`. Do not chain a Python heredoc with other commands in
  the same call, and do not use backslash line continuations.
- Writing files: use a quoted heredoc, `cat > <path> <<'EOF'` … `EOF` — this
  is also how Python source files are written. One file per call, and split a
  large file across several calls (first chunk with `cat >`, the rest with
  `cat >>`): one reply has an output cap, and when a tool call's parameters
  hit it the call is truncated (the error message says so) and the file is
  left incomplete.
- Reading long files: do not `cat` a whole file — use `head -n`, `tail -n`,
  `sed -n 'A,Bp'` and `grep -n` to read the ranges you need. One tool result
  is capped at roughly 40000 characters (less when the context is small);
  beyond that it is truncated, and the message tells you the path of the file
  holding the full text.
- Tool budget: a task gets at most 128 tool calls by default (the user can
  change this in the settings). Plan before you act and skip exploratory
  commands — every call counts. When 10 calls remain you receive a reminder:
  report your progress right away and let the user send "继续" to continue in
  the same conversation (a task that runs out of calls pauses there).
- Network: GET/HEAD requests run without approval — one response is capped at
  16 MiB and a direct connection times out after 60 seconds. Requests with
  side effects (POST, PUT, DELETE, …) need the user's approval. Python code
  cannot reach the network — `pyfetch` and `js.fetch` are intercepted — so
  downloads happen in bash with `curl -o` (§4).
- What Python sees of the filesystem: the data mounts (`/tmp`, `/home/locus`,
  `/mnt/...`) are mirrored into Python under three caps — one file at most
  16 MiB, at most 200 files, at most 25 MiB in total per mount. Anything
  beyond a cap is invisible to Python, and the python command's output ends
  with a marker like `[workspace sync: … NOT visible to Python …]`. If you
  see it, shrink or move the files before packaging.
- `/mnt/upload` is read-only input; `/mnt/workspace` persists across tasks;
  `/mnt/download` is where deliverables for the user go (the `.locus` is built
  there); `/tmp` is scratch space.
- Helpers defined in an earlier Python block stay alive while the worker lives.
  If a later block fails with `NameError`, the worker restarted: re-run the
  earlier block, then retry. A restart also drops a `test_site` from
  `sys.path` (§4): after a restart, call `sdk.test_site(...)` again before
  importing vendored wheels.

## 4. Third-party wheels as plugins

Once Locus has started there is no package installer — `micropip.install` is
rejected. A third-party library reaches Python only as a plugin of a
capability: exactly one wheel per plugin, the full dependency closure carried
inside the capability, `plugins` listed dependencies-first (D13). Never vendor
a runtime-preinstalled package (`pandas` and its closure, `numpy`, `micropip`,
`packaging`, `python-dateutil`, `pytz`, `six`) and never re-vendor a dist that
another plugin of the same capability already provides — the SDK rejects both.

Run this flow top to bottom. Only step 2 touches the network, and it is pure
downloads in bash; every other step is offline Python.

1. **Look up the publisher metadata.** For a pure-Python wheel: the PyPI
   version JSON, `https://pypi.org/pypi/<name>/<version>/json`. For a
   Pyodide-native wheel: the fixed-version lock file,
   `https://cdn.jsdelivr.net/pyodide/v0.26.4/full/pyodide-lock.json`
   (individual wheel files live beside it under `.../full/<file_name>`).
2. **Download, in one bash call.** One bash call that does nothing but
   download — the metadata JSON files and the wheels themselves, each with
   `curl -fsSL -o <file> <url>` (a leading `mkdir -p` for the target
   directories is fine). Never mix a download call with a Python heredoc.
3. **Verify offline.** `sdk.verify_wheel(wheel_path, metadata_path)` compares
   the wheel's sha256 against the downloaded metadata (PyPI `urls[]`, lock
   `packages[]`). `ok: false` → do not use this wheel: re-download once, then
   try another version or tell the user you could not source a verified copy.
4. **Close the dependency closure.** `sdk.wheel_info(wheel)["requires"]` is
   the raw `Requires-Dist` list. Repeat steps 1–4 for every requirement that
   is not runtime-preinstalled, pinning a version that satisfies the
   constraint, until every dependency is provided by a wheel you will vendor.
   Stop and tell the user when:
   - a dependency has no wheel you can verify (steps 1–3 fail for every
     candidate version) — say what is missing instead of shipping a broken
     closure;
   - a wheel exceeds 16 MiB — the SDK refuses it (`wheel-too-large`), because
     files over 16 MiB are invisible to Locus Python (§3): it cannot be
     packaged in Locus at all, so say so honestly;
   - a native wheel carries the wrong platform tags — only `cp312` /
     `pyodide_2024_0_wasm32` (the runtime's Pyodide 0.26.4 ABI) is accepted;
     look for a matching Pyodide build or fall back to a pure-Python wheel.
5. **Generate the plugins.** For every wheel call
   `sdk.plugin_from_wheel(project_dir, wheel_path)` — dependencies first —
   and write the returned ids into capability.json's `plugins` in that same
   order. Always the SDK: the id is `py-<normalized dist name>` and the
   descriptor is derived from the wheel bytes, so the same dist in another
   capability stays byte-identical and is installed once. A hand-written or
   hand-edited descriptor — even one character different — is rejected at
   import.
6. **Import-test before packaging.** `sdk.test_site([wheel_paths...])`
   extracts the wheels to /opt/locus-site — outside the data mounts, so the
   §3 caps do not apply — and puts it in front of `sys.path`; then import
   each top-level package and exercise the core calls in one Python block.
   After a worker restart, call `test_site` again: the extracted files
   survive, identical wheels are skipped, and the site is re-inserted into
   `sys.path`.
7. **Package** as in §5: `validate` (empty diagnostics) → `build` →
   `inspect`, and check the summary lists every `py-` plugin plus the skill.

## 5. Workflow

1. **Confirm the need.** Restate the request as one sentence; ask one or two
   questions only when the behavior is genuinely ambiguous.
2. **Write the project files** (layout in §2). Keep the first version small:
   one skill, at most one plugin — plus the wheel plugins of §4 when the task
   needs a third-party library.
3. **Test the plugin from source**: put `src/` on `sys.path`, import the
   package, assert the outputs — all in one bash call. Keep the first
   version's tests to 3–5 of the most basic assertions — the core function,
   empty input, one boundary case — get those passing, and only then extend.
   Do not write precise assertions for complex rules (exact counts over
   Chinese text, say) unless the user explicitly asked for that rule. Fix
   failures here, before packaging.
4. **Package** (one bash call):
   `sdk.build_wheel("src", "<dist>", "<version>", "plugins/<plugin-id>/artifacts", summary=…)`
   → `sdk.validate(".")` — the diagnostics list must be empty; every message
   tells you which file and rule failed → `sdk.build(".", "/mnt/download")`
   → `sdk.inspect(result["path"])` and check the summary (id, version,
   components, credentials, file count).
5. **Deliver.** Before delivering, note the newest filename in
   `/home/locus/capability-imports/` so step 6 can tell the new report apart
   from older ones. Then tell the user:
   - the package as a file-card link,
     `[<id>-<version>.locus](sandbox:/mnt/download/<id>-<version>.locus)`,
     which the reply renders as a card with the file name, size and an
     **Import** button (files written to `/mnt/download` during the task are
     also listed below the reply when the task ends);
   - the import step: click **Import** on that file card (or on the package's
     entry in the file list in the right sidebar) and confirm the import
     dialog;
   - what they will see after import: the components (each plugin and skill by
     display name) and, for every declared credential, the exact target
     address (origin + path prefix) their key would be sent to — if there are
     no credentials, say so;
   - that they should tell you once the import is done.
   You can also mention **+ → Capabilities → Add capability** as another way
   to import. Do not try to import the package yourself — you cannot;
   importing is the user's explicit click, and that click is the trust
   decision that turns your output into an installed capability.
6. **Read the import report.** One import attempt writes exactly one report:
   a failed pre-import check writes its report immediately (that is already
   the final report); when the checks pass, the confirm dialog is shown and
   nothing is written until the user clicks Import (the commit report) or
   Cancel (a cancelled report). When the user says the import is done, list
   `/home/locus/capability-imports/` and read the newest file by name — that
   file is the final result of this import. `ok` true (`userAction`
   "confirmed") → show how to use the capability in a next task. `ok` false,
   or `userAction` "cancelled" → fix the listed diagnostics, bump the patch
   version, rebuild, and deliver again. If no report is newer than the one
   you noted in step 5, the import has not finished — the confirm dialog may
   still be open; ask the user to finish it (or cancel) instead of guessing
   from an older report.
7. **Keep credentials honest.** A credential declaration is a promise about
   where the user's key may be sent. Declare the narrowest origin and prefix
   that work, and never change them on a repack without saying so — the user
   must re-confirm changed credentials.

**src/reference_text_tools/__init__.py**

```python
"""Reference text tools: deterministic word counting and term extraction.

Pure Python standard library; no third-party imports.
"""

import re
from collections import Counter

_WORD_RE = re.compile(r"[A-Za-z0-9']+")


def word_count(text):
    """Number of words: maximal runs of ASCII letters, digits or apostrophes."""
    if not isinstance(text, str):
        raise TypeError("word_count expects a string")
    return len(_WORD_RE.findall(text))


def top_terms(text, n=5):
    """The *n* most frequent lowercased terms as (term, count) pairs.

    Ordered by descending count, ties broken alphabetically — deterministic.
    """
    if not isinstance(text, str):
        raise TypeError("top_terms expects a string")
    if isinstance(n, bool) or not isinstance(n, int):
        raise TypeError("top_terms expects an integer n")
    if n < 0:
        raise ValueError("n must not be negative")
    counts = Counter(w.lower() for w in _WORD_RE.findall(text))
    return sorted(counts.items(), key=lambda kv: (-kv[1], kv[0]))[:n]
```

````markdown
# Docx Report

Use the vendored python-docx wheel plugin (import `docx`) to write .docx
files. Every document is built from four element kinds: a heading (the
title), paragraphs, bullet lists and tables.

## Steps

1. Build the document in one Python block and save it under `/mnt/download`;
   deliver the file to the user as a link in the reply,
   `[quarterly-report.docx](sandbox:/mnt/download/quarterly-report.docx)` —
   it renders as a file card with a Download button.
2. Elements:
   - title: `document.add_heading("Title", 0)` (level 0 is the title style);
   - paragraph: `document.add_paragraph("…")`;
   - bullet: `document.add_paragraph("…", style="List Bullet")`;
   - table: `t = document.add_table(rows=2, cols=2)` then
     `t.cell(r, c).text = "…"`.
3. Add exactly what the user asked for; keep the default styling.

```python
from docx import Document

document = Document()
document.add_heading("Quarterly Report", 0)
document.add_paragraph("Generated locally by Word Report Builder.")
for bullet in ("Revenue up 12%", "Two new capabilities installed"):
    document.add_paragraph(bullet, style="List Bullet")
table = document.add_table(rows=2, cols=2)
table.style = "Table Grid"
table.cell(0, 0).text = "Metric"
table.cell(0, 1).text = "Value"
table.cell(1, 0).text = "Reports"
table.cell(1, 1).text = "3"
document.save("/mnt/download/quarterly-report.docx")
print("saved /mnt/download/quarterly-report.docx")
```
````

Verify all three offline (§4 steps 3–4) and read python-docx's requirements —
this is how the three-wheel set above was chosen; neither requirement is
runtime-preinstalled, so both must be vendored. One bash call:

```bash
cd /mnt/workspace/capabilities/word-report-builder
python <<'PY'
import locus_capability_sdk as sdk

VERIFIED = {
    "python_docx-1.2.0-py3-none-any.whl": "/tmp/wheel-meta/python-docx.json",
    "typing_extensions-4.16.0-py3-none-any.whl": "/tmp/wheel-meta/typing-extensions.json",
    "lxml-5.2.1-cp312-cp312-pyodide_2024_0_wasm32.whl": "/tmp/wheel-meta/pyodide-lock.json",
}
for filename, meta in VERIFIED.items():
    r = sdk.verify_wheel("/tmp/wheels/" + filename, meta)
    assert r["ok"], (filename, r["diagnostics"])

info = sdk.wheel_info("/tmp/wheels/python_docx-1.2.0-py3-none-any.whl")
```

## 7. Anti-patterns

- Editing Locus's own source or settings to register the capability, or
  hand-computing hashes and hand-zipping the archive — the SDK plus the user's
  import click are the only path.
- Shipping extra skills/plugins the user did not ask for, or a credential
  declared "just in case" or pointed at an `http://` or private address.
- Repacking edited content under the same version instead of bumping the patch
  part first.
- Hand-writing or hand-editing a third-party wheel's plugin.json — the
  descriptor must come from `sdk.plugin_from_wheel` byte-for-byte; one edited
  character breaks coexistence with the same component in other capabilities
  and the import is rejected.
- Vendoring a runtime-preinstalled package, or a dist that another plugin of
  the same capability already provides, as an extra wheel — dead weight at
  best, a rejected import at worst.
